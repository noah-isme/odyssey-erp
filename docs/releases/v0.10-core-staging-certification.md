# v0.10-core Staging Certification Record

**Status:** Evidence template; this document does not certify a release by
itself.

**Profile:** `v0.10-core`

**Candidate:** `v0.10.0-rc.3`

The staging deployment must run with `RELEASE_PROFILE=v0.10-core`. This profile
contains only the five capabilities marked `v0.10.0 scope=yes` in the
[authoritative feature matrix](../reference/feature-matrix.md). A capability may
be marked `production-certified=yes` only after the corresponding evidence is
attached to this record and reviewed by the release owner.

## Profile and environment controls

- [ ] Staging is isolated from production PostgreSQL, Redis, storage, secrets,
      host paths, and systemd units.
- [ ] `/opt/odyssey-staging/.env` sets `APP_ENV=staging` and
      `RELEASE_PROFILE=v0.10-core`.
- [ ] `CONNECTORS_DEVELOPMENT_MODE=false` and production-like connector
      configuration is verified; no test provider can report success in place of
      a real integration.
- [ ] Session, CSRF, database, Redis, storage, and Gotenberg secrets/endpoints
      are staging-specific and are not copied from production.
- [ ] The exact commit used for the artifact, migrations, and web assets is
      recorded above.

## Migration, recovery, and operational evidence

- [ ] Restore a production-like backup into the isolated staging database and
      run integrity checks before migration.
- [ ] Apply all migrations through the candidate version and record the final
      migration version and schema checksum.
- [ ] Exercise the newest reversible up/down path; record any irreversible
      migrations and the tested recovery procedure.
- [ ] Create and verify a pre-deploy backup, then restore it into a clean
      database and capture the result.
- [ ] Verify `/healthz`, web and worker service status, logs, queue convergence,
      audit events, secure cookies, CSRF/session controls, and alert delivery.
- [ ] Perform the application rollback to the previous verified artifact and
      confirm health; document the database rollback decision separately.
- [ ] Observe the candidate for at least 60 minutes and record error rate,
      latency, queue depth, database/Redis health, and any incidents.

## Tenant and access isolation

- [ ] Test with at least two companies and branch-scoped users.
- [ ] Direct URLs, form payloads, company/branch changes, expired assignments,
      and worker inputs cannot cross an authorized scope.
- [ ] Revoking an assignment through the access-review workflow removes access
      without requiring a stale session to be trusted.
- [ ] No-access users receive the documented denied/no-access behavior.

## Promotion decision

The release owner may promote only when every row above is `pass`, all required
operational evidence is attached, no critical/high finding is open, and the
candidate passes the final gate from a clean, tagged checkout:

```bash
RELEASE_PROFILE=v0.10-core make production-release-check
```

Until then, the candidate remains a release candidate and every in-scope matrix
row remains `production-certified=no`.

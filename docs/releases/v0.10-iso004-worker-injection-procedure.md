# ISO-004 Worker Injection Procedure (v0.10-core)

**Purpose:** the operator procedure for certification row `ISO-004` (forged, retried and
duplicate worker inputs). It resolves operator prerequisite item 8 in
[v0.10-operator-lane-prerequisites.md](v0.10-operator-lane-prerequisites.md): the
documented injection path is a direct asynq enqueue into the staging Redis, driven by the
`scripts/certification/iso004` tool, with Postgres observed read-only.

**Scope:** staging only. Nothing here may touch production hosts, DSNs or Redis.

**Verification status:** this document was written from the tool source on the
certification branch. Everything that depends on the real staging host (worker unit
contents, SMTP sink, Redis reachability, the live schema, who owns which files) is marked
**[verify on staging]** and is not confirmed by this document.

## 1. What the tool does

`go run ./scripts/certification/iso004` enqueues crafted tasks (queue `default`,
`MaxRetry` from `--max-retry`, `Retention(72h)`) with TaskIDs of the form
`iso004:<run-id>:<scenario>:<n>`, waits for each scenario to converge, takes read-only SQL
snapshots before and after, evaluates assertions, and writes an evidence bundle to `--out`.
Every Redis observation is filtered by the run's TaskID prefix and SQL is scoped to the
company A/B fixture IDs, so unrelated cron or sweep activity cannot flip an assertion.

Tier 1 scenarios (registry order in `scripts/certification/iso004/scenarios.go`):

| ID | What it proves |
|---|---|
| `S01-unregistered-type` | unregistered task type converges via retry/dead-letter |
| `S02-malformed-payload` | malformed payloads are SkipRetry |
| `S03-object-not-found` | unknown object IDs converge without effects |
| `S05-forged-object-variance` | company-B variance snapshot injected by an unrelated operator |
| `S06-forged-crossscope-ocr` | OCR job whose company disagrees with its document version |
| `S07-duplicate-delivery-variance` | duplicate delivery of the same variance snapshot |
| `S08-unregistered-under-profile` | v0.11-only handlers are not registered under `v0.10-core` |
| `S09-duplicate-delivery-ap` | duplicate delivery of AP invoice processing (three paths) |
| `S09b-forged-actor-ap` | AP invoice processing with a spoofed `created_by` |
| `S10-forged-company-bi-export` | BI export for a forged company (excluded unless `connector_connections` is empty for A and B) |
| `S11-forged-recipient-mail` | recipient-addressed mail tasks with a forged recipient (email) |
| `S12-duplicate-delivery-payslip` | duplicate delivery of a company-B payslip email (email) |

Deferred by decision and written into the evidence details as **deferred, never N/A**
(`deferredScenarios` in `scenarios.go`): `boardpack:generate full generation`,
`documents:ocr legitimate duplicate`, `bankfeeds:event legitimate delivery`.

`--dry-run` prints this plan without contacting Redis or Postgres. Use it first.

## 2. Prerequisites

- SSH to the staging VPS as an operator who can read `/opt/odyssey-staging/.env`
  (for `REDIS_ADDR`) and the journal for `odyssey-staging-worker.service`
  (see [v0.10-staging-preflight-checklist.md](v0.10-staging-preflight-checklist.md) section D).
  The tool needs network access to the staging Redis, so running it on the VPS is the
  expected path.
- `odyssey-staging-worker.service` active, running the candidate release
  (`RELEASE_PROFILE=v0.10-core`). Gotenberg must be reachable from the worker for `S12`
  (the payslip email attaches a PDF rendered through it,
  `internal/payroll/payslip.go` `Render`); no other Tier 1 scenario uses it.
- A Go toolchain on the operator host, or a binary built from the certification branch.
  The tool and the seeder are plain `go run` / `go build` targets; they do not need
  `golangci-lint`, so a host without the linter can still build and run them.
  Example: `go build -o iso004 ./scripts/certification/iso004`.
- A **write** DSN for the one-time fixture seed (section 5) and a separate **read-only**
  DSN for the tool (`--dsn`, or `STAGING_CERT_PG_DSN`, then `PG_DSN`). The tool also
  forces every pooled connection read-only and fails preflight if the session is not.
- The automated certification workflow's `GITHUB_RUN_ID` (section 4).
- A reviewer name for the evidence record.
- For email scenarios: a Mailpit or MailHog sink behind the worker's SMTP settings and its
  HTTP API reachable from the operator host (section 6).
- Auto-post prerequisites (section 7).

## 3. Ordering

ISO-004 runs **after OPS-003** (queue delivery/retry/dead-letter, audit, alerts) and
**before OPS-004** (rollback), matching step 8 of the execution order in
[v0.10-operator-lane-prerequisites.md](v0.10-operator-lane-prerequisites.md). Running it
after OPS-004 would test a rolled-back release; OPS-005's observation window starts only
after the OPS-004 final restore, so ISO-004 noise must not fall inside it.

## 4. Run ID decision

The operator lane **reuses the automated certification workflow's `GITHUB_RUN_ID`**
(decided 2026-10-04). The same value is:

- `--run-id` for the tool (must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`; it appears in
  every TaskID and in a Redis SCAN glob),
- `--iso004-key` for the seeder (must match `^[A-Za-z0-9][A-Za-z0-9-]{0,39}$`, so no `.`
  or `_`; a numeric GitHub run ID satisfies both),
- the `GITHUB_RUN_ID` exported when running `scripts/staging-certification-evidence.sh`.

A run ID can be used for **one** tool run. Preflight fails (`redis.run_prefix_unused`) if
any task with the prefix `iso004:<run-id>:` already exists in any queue. Never delete tasks
or change the run ID to get around that; see the no-silent-rerun rule in section 10.

## 5. Fixture seed

Two seed commands exist, and both run behind the same staging guard:

- **Base seeder** (`go run ./scripts/seed/staging` without `--iso004`) creates the
  v0.10-core certification fixtures: companies `ODY-01`/`ODY-02`, branches, warehouse,
  master data, the admin/branch/no-access test identities, the ISO-003 rows and the
  document classification/category/retention policy. `--iso004` needs these as
  prerequisites (it aborts with `missing prerequisite: ...` otherwise).
- **`--iso004` extension** creates the ISO-004 fixtures for one run key. It never calls the
  base seeder.

Run the base seeder only when the core fixtures are not already present on the staging
database; rerunning it is safe but unnecessary.

The base seeder was rewritten for the schema at migration 000124 (it previously inserted
into columns that no longer exist, for example `customers.address`, and used conflict
targets that are not unique constraints, so it failed on a migrated database). It now has
the same safety properties as `--iso004`:

- it refuses to run unless `APP_ENV=staging`, an explicit `--dsn`/`PG_DSN` is given (the
  localhost default is gone), the DSN has exactly one host and an explicit `dbname`, the
  host and database equal `--confirm-staging <db>@<host>` and `current_database()`, and the
  host does not match `--deny-host-regex`;
- every insert is `ON CONFLICT DO NOTHING RETURNING ...`, and the SQL contains no
  `UPDATE`/`DELETE` (a unit test scans for this), so it never changes a row it did not
  create in this run;
- when an insert is suppressed by an existing row, that row is read back and must be in the
  expected scope (branch in `ODY-01`/`ODY-02`, warehouse in the HQ branch, customer,
  supplier, product and category in `ODY-01`, active, and so on); an existing test user must
  already have the configured password and be active, and the branch/no-access users must
  hold no global role. Any mismatch aborts the whole run and rolls the transaction back;
- everything runs in one transaction under an advisory lock.

If it refuses because a fixture already exists in another company, or a test user has a
different password, fix the data or the `STAGING_CERT_*` variables; do not edit the seeder
to overwrite. Its stdout is unchanged (the 12 `STAGING_CERT_*` values; `--json`, `--export`
and `--apply-gh` behave as before); a per-row `created`/`reused` report goes to stderr. A
rerun reports `0 created` and the same IDs.

Verified locally against a throwaway Postgres 15 with all 124 migrations applied (clean
apply, no-op rerun, then `--iso004`), and by DB-gated tests (`STAGING_SEED_PG_DSN`, see
`scripts/seed/staging/base_seed_db_test.go`). Not yet run against the real staging
database. **[verify on staging]** with `--confirm-staging` and `APP_ENV=staging`.

Base seeder (only if the core fixtures are missing), then the ISO-004 dry run (guard plus
SELECT-only resolution, writes nothing) and the real ISO-004 seed:

```bash
export APP_ENV=staging
export PG_DSN='<write DSN for the staging DB>'   # never commit; never pass a prod DSN

go run ./scripts/seed/staging --confirm-staging <db-name>@<db-host> --json > base-fixtures.json

go run ./scripts/seed/staging --iso004 --iso004-key "$RUN_ID" \
  --confirm-staging <db-name>@<db-host> --dry-run

go run ./scripts/seed/staging --iso004 --iso004-key "$RUN_ID" \
  --confirm-staging <db-name>@<db-host> --json > fixtures.json
```

Flags (all in `scripts/seed/staging/main.go`):

| Flag | Meaning |
|---|---|
| `--iso004` | run only the ISO-004 extension (without it, the base seeder runs) |
| `--iso004-key` | the run ID; required with `--iso004` |
| `--confirm-staging <db>@<host>` | must match the DSN database and host and `current_database()`; required by the base seeder and by `--iso004` |
| `--deny-host-regex` | refuse when the DSN host matches this case-insensitive regex (default `prod`) |
| `--dry-run` | only valid with `--iso004`; guard and resolution, prints planned inserts, writes nothing |
| `--dsn` | explicit DSN; otherwise `PG_DSN`. The localhost default is **not** used by either seeder |
| `--json` | print fixtures as JSON (the `STAGING_CERT_ISO004_*` values the tool consumes) |
| `--export` | print shell `export` lines instead |
| `--apply-gh` | also set the values as GitHub `staging` environment variables via `gh`; not needed for this procedure |

The guard refuses unless `APP_ENV=staging`, the DSN has exactly one host and an explicit
`dbname`, and host and database equal the `--confirm-staging` value. Keep `fixtures.json`
with the evidence; it contains IDs and a synthetic payslip address, not credentials.

The seed prints `WARNING: not satisfied: ...` lines for the prerequisites in section 7. The
seed only warns; it does not create them.

## 6. Email gate

Email scenarios (`S11`, `S12`; they send `mail:send`, `email:deliver` and a payslip
email) are enabled only when **both** are true:

1. `--allow-email` is passed (this also requires `--mail-api`), and
2. the SMTP sink preflight passes.

The preflight resolves the worker's real SMTP target by inspecting
`systemctl show -p Environment -p EnvironmentFile <worker-unit>` (inline `Environment=`
first, then each `EnvironmentFile` in order, later definitions overriding earlier ones;
unset values fall back to the application defaults `127.0.0.1:1025`). It then requires:

- `SMTP_HOST` is loopback (a literal 127.0.0.0/8 or `::1` address, or `localhost` resolving
  only to loopback; any other name is rejected even if it resolves to loopback),
- the SMTP greeting is a `220` line that identifies **Mailpit or MailHog**, and
- the `--mail-api` URL answers like Mailpit or MailHog.

**Loopback alone is not sufficient.** If any check fails, the email gate is recorded as
failed in `preflight.json` with reasons, the email scenarios are excluded, and an excluded
scenario makes the overall run FAIL (exit 1). Never work around that by pointing the worker
at a real relay. If the worker unit overrides `SMTP_HOST`/`SMTP_PORT` through a drop-in or
`EnvironmentFile`, the tool will read that; check with
`systemctl show -p Environment -p EnvironmentFile odyssey-staging-worker.service`.
**[verify on staging]** what the unit actually sets and that a sink is listening.

For a local rehearsal, `--worker-env <file>` (repeatable) replaces the unit's
`EnvironmentFile` list. Do not use it on staging.

## 7. Auto-post prerequisites the seed only warns about

The seed's `ISO004-AP-B-MATCHED` invoice is expected to auto-post. That needs, in the
shared configuration:

- an `OPEN` `periods` row whose dates cover today, and
- `account_mappings` rows for module `AP`, keys `ap.invoice.inventory` and `ap.invoice.ap`.

If these are missing the seed prints a warning, the matched path records `CLOSED_PERIOD`
and the S09 assertions will not pass. Fix the configuration through the normal
administrative path **before** the run, or accept and record the failure; do not edit
fixture or period rows by hand during the run. **[verify on staging]**

Also checked by the tool's preflight (not the seed): there must be no active global AP
matching policy (`company_id IS NULL AND supplier_id IS NULL`); otherwise the S09
`MISSING_MAPPING` path is FAIL-by-precondition.

## 8. Run

### 8.1 Dry run

```bash
go run ./scripts/certification/iso004 --dry-run \
  --candidate-tag v0.10.0-rc.9 --candidate-sha <40-hex candidate commit> \
  --run-id "$RUN_ID" --fixtures fixtures.json \
  --allow-email --mail-api http://127.0.0.1:8025 --reviewer "<name>" \
  --out /var/lib/odyssey-evidence/iso-004
```

Substitute the actual candidate tag and commit under test (the tag must match
`^v0\.10\.0-rc\.[1-9][0-9]*$`, the SHA is 40 lowercase hex). The dry run prints every task,
payload, expectation, assertion, mail recipient and the deferred list, and runs only static
checks (fixtures, and `RELEASE_IDENTITY` when readable). It writes nothing. Review the plan
and the "static checks" block; a non-zero exit means the fixtures are incomplete.

### 8.2 Real run

Only after you understand the email gate (section 6):

```bash
START_UTC=$(date -u +%Y-%m-%dT%H:%M:%SZ)
set -a; . /opt/odyssey-staging/.env; set +a        # REDIS_ADDR  [verify on staging]
export STAGING_CERT_PG_DSN='<read-only DSN>'

go run ./scripts/certification/iso004 \
  --candidate-tag v0.10.0-rc.9 --candidate-sha <40-hex candidate commit> \
  --run-id "$RUN_ID" --fixtures fixtures.json \
  --allow-email --mail-api http://127.0.0.1:8025 --reviewer "<name>" \
  --out /var/lib/odyssey-evidence/iso-004
END_UTC=$(date -u +%Y-%m-%dT%H:%M:%SZ)
```

Run flags (`scripts/certification/iso004/config.go`):

| Flag | Default | Notes |
|---|---|---|
| `--run-id` | required | see section 4 |
| `--out` | required | must not exist or be empty |
| `--candidate-tag`, `--candidate-sha` | required | must equal the deployed worker's `RELEASE_IDENTITY` |
| `--release-identity` | `/opt/odyssey-staging/current/RELEASE_IDENTITY` | preflight requires tag and commit to match |
| `--redis` | `$REDIS_ADDR` | host:port or `redis://` URL; credentials are redacted in outputs |
| `--dsn` | `$STAGING_CERT_PG_DSN`, then `$PG_DSN` | must be read-only |
| `--fixtures` | none | JSON from `--iso004 --json`; `STAGING_CERT_ISO004_*` env vars are the fallback |
| `--scenarios` | all Tier 1 | comma-separated IDs; **rehearsal only**: a subset is recorded as `subset N of M` and its evidence result is always FAIL (see below). Certification uses the default |
| `--max-retry` | 2 (allowed 1-25) | see section 11 |
| `--timeout` | 15m | convergence wait **per scenario** (all phases of that scenario share it) |
| `--poll` | 2s | task state poll interval; must not exceed `--timeout` |
| `--worker-unit` | `odyssey-staging-worker.service` | inspected for SMTP settings |
| `--worker-env` | none | rehearsal override of the unit's env files |
| `--mail-api` | none | Mailpit/MailHog API base URL; required with `--allow-email` |
| `--allow-email` | off | enables email scenarios, still gated |
| `--reviewer` | `REVIEWER_PENDING` | written into the evidence details; no control characters, `;`, `<`, `>` |
| `--dry-run` | off | print the plan only |

Exit codes: `0` every Tier 1 scenario ran and evaluated PASS; `1` preflight failed, or any
scenario FAIL or EXCLUDED, or `--scenarios` left a Tier 1 scenario out, or the bundle could
not be written fully; `2` usage or
configuration error; `3` preflight passed but the build has no scenario executor, nothing
was enqueued (wrong or partial build); `4` tasks were enqueued but nothing evaluated them
(the run is not PASS; keep the bundle and treat it as a finding).

**A `--scenarios` subset is a rehearsal and is never PASS.** ISO-004 is certified only by
one run of every Tier 1 scenario. When any Tier 1 scenario is not run, the tool still
writes a full bundle, but the evidence record has `"result":"FAIL"`, the exit code is `1`,
`summary.json` and `summary.md` list a reason of the form `rehearsal/subset run, not
certification evidence: K of N Tier 1 scenarios not run: <IDs>`, and the record's `details`
say `scenarios (subset K of N Tier 1): ...` followed by `REHEARSAL/SUBSET RUN, NOT
CERTIFICATION EVIDENCE (result is never PASS); scenarios not run: <IDs>`. The scenarios
that did run keep their own PASS/FAIL rows. This is handled the same way as an excluded
scenario: the rest of the bundle is kept as a finding, nothing is relabelled N/A (the
closeout script rejects N/A for a mandatory row), and the FAIL record must never be edited
to PASS or registered as the ISO-004 row. Use a subset to rehearse or to debug one
scenario; then do the certification run with the default selection.

Preflight (`preflight.json`) checks, among others: fixtures load and validate,
`RELEASE_IDENTITY` match, Redis ping, an active asynq server consuming `default` that
reports the candidate identity, queue not paused, unused run prefix, DB read-only session,
fixture ownership probes, no `connector_connections` for companies A and B (else S10 is
excluded), and the email gate. A fatal preflight failure enqueues nothing.

### 8.3 Capture the worker journal

```bash
journalctl -u odyssey-staging-worker.service \
  --since "$START_UTC" --until "$END_UTC" --no-pager \
  > /var/lib/odyssey-evidence/iso-004/worker-journal.log
```

Take the window from before the tool started to after it exited. Daily and every-minute
cron noise from other tasks will appear in it; that is expected and is why the tool filters
by TaskID prefix.

### 8.4 Seal

Adding `worker-journal.log` invalidates the `SHA256SUMS` the tool wrote. Regenerate it with
the tool's `seal` subcommand:

```bash
go run ./scripts/certification/iso004 seal --out /var/lib/odyssey-evidence/iso-004
```

### 8.5 Bundle contents

`preflight.json`, `run.json`, `summary.json`, `summary.md`, `archived-tasks.json`,
`candidate.txt`, `evidence-record.log`, `SHA256SUMS`, `scenarios/<id>/` raw artifacts
(before/after SQL, timelines, task states), and `worker-journal.log` after step 8.3.
`archived-tasks.json` must list exactly the run's archived tasks.

## 9. Register the row

1. Copy the whole `--out` directory into the operator candidate directory as
   `iso-004-worker-injection/`.
2. Append the single line from `evidence-record.log` to the candidate's
   `staging-certification.log`, replacing `REVIEWER_PENDING` with the reviewer's name if
   `--reviewer` was not used. The line has the shape
   `CERTIFICATION_EVIDENCE evidence_id=ISO-004 {"evidence_id":"ISO-004","result":"<PASS|FAIL>","collected_utc":"...","details":"iso-004-worker-injection/summary.json reviewed by <name>; ..."}`.
3. Single-row rehearsal of the collector (local only, no upload):

   ```bash
   GITHUB_RUN_ID=<automated run id> scripts/staging-certification-evidence.sh \
     --candidate <operator-candidate> --evidence <evidence-dir> --lane operator \
     --contract scripts/staging-certification-contract.json \
     --expected-evidence-ids ISO-004 --local-only
   ```

4. Once all 11 operator rows have records, run the real lane, first local-only and then
   with upload:

   ```bash
   GITHUB_RUN_ID=<automated run id> scripts/staging-certification-evidence.sh \
     --candidate <operator-candidate> --evidence <evidence-dir> --lane operator \
     --contract scripts/staging-certification-contract.json --local-only
   # then the same command without --local-only (needs the S3 Object Lock settings)
   ```

5. Continue with closeout per
   [v0.10-core-staging-certification.md](v0.10-core-staging-certification.md).

**Secret-redaction risk.** `scripts/staging-certification-evidence.sh` copies the candidate
into the evidence directory and rewrites secret-like text in every text file (for example
`password=...`, `token: "..."`, `Bearer ...`, `postgres://user:pass@`). It then writes its own
`SHA256SUMS`. If the ISO-004 bundle contains text of that shape (the worker journal or
copied task payloads can), the copied files differ from your sealed bundle and the
tool's `SHA256SUMS` no longer verifies. After the copy, run
`(cd <evidence-dir>/iso-004-worker-injection && sha256sum -c SHA256SUMS)`; if it fails,
diff the file against the original, record what was redacted, and decide with the
reviewer; do not hand-edit evidence so that the sums pass. **[verify on staging]**
whether the real journal triggers redaction.

## 10. Rules

- A failed scenario stays `FAIL`. It becomes a `FIND-xxx` row whose evidence is the raw
  `scenarios/<id>/` artifacts. Never change a result to PASS.
- **No silent reruns.** Do not rerun "to fix" a result without keeping the first bundle
  untouched. A rerun needs a new run ID, a new bundle directory, and an explicit record of
  why, referencing the first run.
- **Cleanup only after the bundle's `SHA256SUMS` has been uploaded** (the operator lane
  upload in section 9). The task records and Redis keys are part of the evidence until
  then.
- **Never enqueue** `fixed_assets:depreciate`, `documents:disposition`, `fx:daily-rates`,
  `bankfeeds:sync`, or any sweep/scan task as part of ISO-004. The tool does not; do not
  add them by hand.
- Do not run the base seeder, and do not run the tool against production.
- Defects of the superseded rc.8 candidate (`ap:invoice_process` duplicate runs and trusted
  `created_by`; `payroll:payslip_email` re-send on redelivery) are fixed in rc.9
  (`internal/ap/orchestrator.go` `ProcessInvoice`, `internal/payroll/repository.go`
  `DeliverPayslipOnce`), and `S09`, `S09b` and `S12` assert the fixed behavior. If the
  candidate still shows them, the scenario is FAIL and becomes a finding.

## 11. Limits and findings to record

**Timing fidelity.** The tool enqueues with `MaxRetry(2)`; production producers use 3-25
with the same backoff and dead-letter path. The evidence details state this explicitly
(`timing: MaxRetry(2) vs production 3-25 ...`). Convergence waits are per scenario
(`--timeout`).

**`branch` is N/A.** No worker payload struct carries a branch field. The tool checks this
at run time by reflecting over the payload structs and writes
`branch: N/A (no worker payload carries branch_id at <sha>; see jobs/tasks.go, jobs/bi_export.go, jobs/cash_forecast.go, jobs/bank_feeds.go, jobs/ap_invoice.go, jobs/document_ocr.go)`
into the evidence details. If a branch field ever appears, the claim fails and the record
is FAIL.

**Sweep locking gaps are OPS-003 findings.** rc.9 closed two of the claim gaps the sweeps
previously had: `connectors:outbox_sweep` now claims each command with a lease before the
adapter runs (`internal/connectors/outbox_worker.go` `processCommand`), and payslip
delivery locks the undelivered row (`DeliverPayslipOnce`), which the
`payroll:payslip_dispatch` sweep relies on. The gaps that remain are not forged-input
targets for ISO-004 and are pre-recorded in the certification record
([findings](v0.10-core-staging-certification.md#findings)): `crm:reminder_dispatch`
(`FIND-001`), `invoices:scan_overdue` (`FIND-002`) and `cmms:pm_generator_scan`
(`FIND-007`). Attach the reproduction to the existing row instead of raising a duplicate.
`cashforecast:refresh` and `bankfeeds:event` are not registered under `v0.10-core` in rc.9
(`S08`), and `analytics:bi_export` is not registered either (`S10`, `FIND-004`); they
converge as "handler not found".

**Daily cron noise.** `invoices:scan_overdue` emails `customer@example.com` for posted
overdue AR invoices and every-minute sweeps run regardless; this is why the worker journal
for the window is captured.

**TaskID reuse.** asynq frees a TaskID only after the task is deleted; with
`Retention(72h)` the duplicate-delivery conflict check in S07 is deterministic for 72
hours.

## 12. Cleanup

After the sealed bundle (`SHA256SUMS` included) is uploaded:

```bash
go run ./scripts/certification/iso004 cleanup \
  --run-id "$RUN_ID" --out /var/lib/odyssey-evidence/iso-004 --redis "$REDIS_ADDR"
```

`--out` is the sealed bundle (read-only for cleanup). The cleanup record is written outside
it, to `<parent of --out>/cleanup/<run-id>/` (for `--out /var/lib/odyssey-evidence/iso-004`
that is `/var/lib/odyssey-evidence/cleanup/<run-id>/`), so the sealed bundle and its
`SHA256SUMS` stay unchanged. `--queue` (repeatable, default `default`) names the queue(s)
the run used. Only TaskIDs starting with `iso004:<run-id>:` are deleted (per
`cleanup.go`'s flag help). Fixture rows from `--iso004` are company A/B data owned by
the key and are idempotent; they are left in place unless the reviewer decides otherwise.

## 13. Acceptance

The row can be registered when: `preflight.json` shows the candidate worker server and
`RELEASE_IDENTITY` matching; every `scenarios/<id>/` directory holds the raw before/after
SQL and timelines; `archived-tasks.json` lists exactly the run's archived tasks; journal
lines for the run's TaskIDs are present in `worker-journal.log`; `sha256sum -c SHA256SUMS`
passes after sealing and again after the evidence-script copy; and the record's `result`
matches `summary.json`.

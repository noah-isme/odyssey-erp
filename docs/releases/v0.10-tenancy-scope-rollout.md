# v0.10 tenancy scope rollout (from v0.10.0-rc.11)

Status: current operator runbook for every environment that moves from
`v0.10.0-rc.10` (or earlier) to `v0.10.0-rc.11` or later.

## What changes

Up to `v0.10.0-rc.10` every signed-in user saw every company in the workspace
company selector, `/company/select` accepted any existing company, and a
session without a company was silently given the company with the lowest id.

From `v0.10.0-rc.11`:

- The companies a user may work in are the companies of their **active**
  `rbac_user_role_assignments` rows (`valid_from <= NOW()` and `valid_to` NULL
  or in the future), company-wide (`branch_id IS NULL`) or branch-scoped.
- Holders of a role named in `RBAC_GLOBAL_ROLES` (comma separated,
  case-insensitive, matched against the user's `user_roles`) see every
  company. The default is empty: nobody is cross-company unless configured.
- The list is ordered by company **name, then id**. A new session starts in
  the first company of that list (previously: the lowest company id).
- The session company is re-checked on every request. A company that is no
  longer permitted (assignment expired or revoked) is replaced by the first
  permitted company; a user with none has no active company.
- `/company/select` refuses a company outside the list with the existing error
  flash ("Perusahaan tidak ditemukan") and a `303`.
- `/api/me` returns the scoped `companies` list (empty when none),
  `activeCompanyID` (`0` when none) and `releaseProfile`.
- Company-scoped route groups (`/finance/ar`, `/finance/ap`,
  `/finance/banking`, `/finance/bankfeeds`, `/finance/forecasting`,
  `/finance/treasury`, `/sales`, `/delivery`,
  `/inventory`, `/documents`, `/cmms`, `/hr/employees`, `/hr/leave`,
  `/hr/attendance`, `/board-packs`, `/variance`, `/accounting/periods`,
  `/close-runs`) answer `403` to a signed-in user without an active company.
  `/`, `/auth/*`, `/api/me`, `/company/select`, `/settings` and `/healthz` stay
  reachable; `/` shows a "no company assigned" notice.
- Permissions are unchanged: they still come only from `user_roles`. An
  assignment controls which companies a user may select, not what they may do.

The startup log line `rbac global roles` lists the configured
`RBAC_GLOBAL_ROLES` after normalisation.

### Company 0 means "all companies" in some queries

These predicates treat company `0` as every company and are left unchanged in
rc.11. They are reachable only by internal callers, because the route groups
above refuse a session without a company:

- `internal/hr/employees/service.go` (`List`: `$1=0 OR e.company_id=$1`)
- `sql/queries/close.sql` line 13
- `sql/queries/boardpack.sql` lines 89 and 132
- `sql/queries/variance.sql` line 11

### What ISO-002 proves after this change

The company list, the company selector and `/company/select` are scoped to the
user's assignments, and a forged selection leaves the active company
unchanged. AR and AP objects are still **not** company-filtered inside their
handlers: a direct URL to another company's invoice id is not refused by the
tenancy scope. That gap is pre-existing, recorded and deferred.

Delivery orders are company-checked from rc.11 on: the show and edit pages,
the update, confirm, ship, complete and cancel posts, the return form and
create-return answer `404` for another company's order and change no status
or stock, and a delivery order or return cannot use another company's
warehouse (`FIND-036`, resolved in rc.11, `d2ef000`, `b31ad7b`). Return
show, confirm and cancel fail for every company until `FIND-039` is fixed;
their company checks are proven at service level only. The sales-order line
fulfillment warehouse is not checked (`FIND-040`). The other unscoped
handlers of `FIND-032` remain. ISO-002 on rc.11 proves the company list,
`/company/select` and the delivery routes' order and return scoping; AR
invoice and credit-note creation from a delivery order or return still load
it by id alone (`FIND-032`).

## Who is affected

1. Users whose `user_roles` rows existed when migration `000124` ran already
   hold a company-wide assignment (marker `valid_from = 1970-01-01`) in every
   company that existed at that time. They are unaffected.
2. Users granted a role **after** `000124` (UI role grants, `make seed` before
   rc.11, `cmd/bootstrap-admin` before rc.11) have no assignment and would see
   no company after the upgrade. They need the backfill below.
3. Companies created after `000124` are visible only through explicit
   assignments or a role listed in `RBAC_GLOBAL_ROLES`.
4. From rc.11, `cmd/bootstrap-admin` and the dev seed (`scripts/seed/main.go`)
   grant company-wide assignments in every company that exists when they run.
   Re-run `cmd/bootstrap-admin` after creating a company if the administrator
   must see it.

## Before deploying rc.11 to an existing environment

Run every statement below with a role that can write the RBAC tables, record
the outputs as evidence, and deploy only after the "find" query returns the
rows you decided to leave without access.

### Step 1: find users without an active assignment (read-only)

Run before and after the backfill.

```sql
SELECT u.id AS user_id, u.email, r.id AS role_id, r.name AS role_name
FROM user_roles ur
JOIN users u ON u.id = ur.user_id
JOIN roles r ON r.id = ur.role_id
WHERE NOT EXISTS (
    SELECT 1
    FROM rbac_user_role_assignments a
    WHERE a.user_id = ur.user_id
      AND a.valid_from <= NOW()
      AND (a.valid_to IS NULL OR a.valid_to > NOW())
)
ORDER BY u.email, r.name;
```

For each listed user decide which companies they must work in. The default
recommendation is the primary company only. **Never** backfill with a blind
`companies CROSS JOIN user_roles`: that grants every legacy user every company.

### Step 2: expire assignments of revoked legacy roles

Migration `000124` materialised every legacy role as an assignment with
`valid_to NULL`. A role removed from `user_roles` since then would still grant
company visibility. List them first:

```sql
SELECT a.id, a.company_id, a.user_id, a.role_id
FROM rbac_user_role_assignments a
WHERE a.valid_from = TIMESTAMPTZ '1970-01-01 00:00:00+00'
  AND a.branch_id IS NULL
  AND a.valid_to IS NULL
  AND NOT EXISTS (
      SELECT 1 FROM user_roles ur
      WHERE ur.user_id = a.user_id AND ur.role_id = a.role_id
  )
ORDER BY a.user_id, a.company_id;
```

Then expire exactly those marker rows and record the row count:

```sql
BEGIN;
UPDATE rbac_user_role_assignments a
SET valid_to = NOW()
WHERE a.valid_from = TIMESTAMPTZ '1970-01-01 00:00:00+00'
  AND a.branch_id IS NULL
  AND a.valid_to IS NULL
  AND NOT EXISTS (
      SELECT 1 FROM user_roles ur
      WHERE ur.user_id = a.user_id AND ur.role_id = a.role_id
  );
-- check the reported row count against the listing above, then:
COMMIT;
```

Scope: only the `000124` marker rows (`valid_from = 1970-01-01`, company-wide,
open-ended). Run it **before seeding** on an existing environment. Do **not**
run it on the rebuilt staging database: the seeded branch user's
`staging-branch-user` assignment deliberately has no `user_roles` row, and
expiring it would fail ISO-001.

### Step 3: backfill the chosen companies, one company at a time

Replace `:company_id` with one chosen company id and `:user_ids` with the users
you decided should work in it. Repeat per company and record each row count.

```sql
BEGIN;
INSERT INTO rbac_user_role_assignments
    (company_id, user_id, role_id, branch_id, valid_from, valid_to)
SELECT :company_id, ur.user_id, ur.role_id, NULL, TIMESTAMPTZ '1970-01-01 00:00:00+00', NULL
FROM user_roles ur
WHERE ur.user_id = ANY(:user_ids)
  AND NOT EXISTS (
      SELECT 1
      FROM rbac_user_role_assignments a
      WHERE a.user_id = ur.user_id
        AND a.valid_from <= NOW()
        AND (a.valid_to IS NULL OR a.valid_to > NOW())
  )
ON CONFLICT (company_id, user_id, role_id, valid_from) WHERE branch_id IS NULL
DO NOTHING;
-- record the inserted row count for this company, then:
COMMIT;
```

The `NOT EXISTS` clause limits the backfill to users who had no active
assignment when the statement started, so an already-scoped user is not
widened by a later company's run. When the same user must work in several
companies, drop that clause for the second and later companies of that user
only, and record why.

### Step 4: configure `RBAC_GLOBAL_ROLES`

Leave it empty unless a role is deliberately cross-company. Production sets it
only for such roles. Staging leaves it empty: there is no global operator
identity on staging, and the certification administrator has one company-wide
assignment in the primary company only.

### Step 5: verify after deploy

- Re-run the Step 1 query; only users you decided to leave without access
  remain.
- Sign in as a scoped user: `GET /api/me` lists only the assigned companies,
  `releaseProfile` matches `RELEASE_PROFILE`, and `activeCompanyID` is one of
  them.
- Sign in as a user without an assignment: `GET /` renders the no-company
  notice; `GET /finance/ar/invoices` returns `403`.

## Granting access from rc.11 on

The role screens (and `rbac.Service.AssignRole`) only insert into
`user_roles`; they create no `rbac_user_role_assignments` row. A newly
onboarded user therefore sees no company, `/` shows the no-company notice and
every company-scoped route group answers `403`, until an operator inserts a
company-wide assignment. Until the UI grant creates the assignment (see
`NEXT_STEPS.md`), do this for each new user and each company they must work
in.

Find the user's roles that have no active assignment in that company
(read-only; run before and after the insert):

```sql
SELECT ur.user_id, ur.role_id, r.name AS role_name
FROM user_roles ur
JOIN roles r ON r.id = ur.role_id
WHERE ur.user_id = :user_id
  AND NOT EXISTS (
      SELECT 1
      FROM rbac_user_role_assignments a
      WHERE a.user_id = ur.user_id
        AND a.role_id = ur.role_id
        AND a.company_id = :company_id
        AND a.branch_id IS NULL
        AND a.valid_from <= NOW()
        AND (a.valid_to IS NULL OR a.valid_to > NOW())
  );
```

Insert one company-wide assignment per listed role, for exactly one user and
one company:

```sql
BEGIN;
INSERT INTO rbac_user_role_assignments
    (company_id, user_id, role_id, branch_id, valid_from, valid_to)
SELECT :company_id, ur.user_id, ur.role_id, NULL, NOW(), NULL
FROM user_roles ur
WHERE ur.user_id = :user_id
  AND NOT EXISTS (
      SELECT 1
      FROM rbac_user_role_assignments a
      WHERE a.user_id = ur.user_id
        AND a.role_id = ur.role_id
        AND a.company_id = :company_id
        AND a.branch_id IS NULL
        AND a.valid_from <= NOW()
        AND (a.valid_to IS NULL OR a.valid_to > NOW())
  )
ON CONFLICT (company_id, user_id, role_id, valid_from) WHERE branch_id IS NULL
DO NOTHING;
-- the row count must equal the number of rows the find query listed; then:
COMMIT;
```

After the commit the find query returns no rows for that user and company,
and the user's next request lands in the company (`GET /api/me` lists it).
Never run the insert without `:user_id` and `:company_id` bound to single
values. A role removed later still needs `valid_to` set on these rows, as
described in the next section.

## Revoking access from rc.11 on

The role screens only delete from `user_roles`. Every revocation must also set
`valid_to = NOW()` on that user's matching `rbac_user_role_assignments` rows,
otherwise the user keeps seeing the company (without permissions). The
permanent fix belongs to the v0.11 scoped-permission design.

# Approval Finalization Defect: Data Remediation

Applies to every environment that ran a build containing commit `6f50f41`
(`feat(approvals): add configurable approval engine`), which includes tags
`v0.10.0-rc.1` through `v0.10.0-rc.9`. The code fix is
`fix(approvals): return post-decision request from Decide`, first shipped in
`v0.10.0-rc.10`. Deploying it stops new damage. It does not
repair rows that are already wrong.

## What went wrong

`approvals.Repository.Decide` returned the request as it looked before the
decision. Only rejection refreshed it. The approval engine row itself is
correct (`approval_requests.status = 'APPROVED'`), but on a final approval each
module's finalizer received status `PENDING`. Each module handled that value
differently:

| Module | Finalizer behaviour with `PENDING` | Resulting document state |
|---|---|---|
| `LEAVE` | Treated as rejection | `hr_leave_requests.status = 'REJECTED'`; balance `pending` released but `used` never incremented; false `LEAVE_REJECTED` audit row under the approver |
| `PO` | Treated as rejection | `pos.status = 'CANCELLED'`, `approved_by`/`approved_at` NULL; false `reject` row in the legacy `approvals` log |
| `RFQ_AWARD` | Treated as rejection | `rfq_awards.status = 'REJECTED'`, no POs generated; false `RFQ_AWARD_REJECT` audit row |
| `PAYROLL` | Returned `ErrInvalidState` after the approval had committed | `payroll_runs.status` stuck at `APPROVAL`, pointing at an APPROVED request, with no journal |

Two smaller effects:

- Requesters received an "approved" notification whose body said the
  document "was PENDING".
- On multi-step policies, approvers of step 2 and later were never sent an
  assignment notification. Their items still appear in `/approvals` and still
  escalate.

The same commit also fixes the step quorum count, which counted approvals
across all requests instead of the request being decided. That only matters
for steps with `required_approvals > 1`. The policy UI always creates
`required_approvals = 1`, so only policies inserted directly in the database
can be affected.

## Rules for remediation

- Deploy the fix first. Otherwise new rows keep breaking while you repair old
  ones.
- Every query in the **Find** sections is read-only. Run them against a replica
  or a read-only session first.
- Repair row by row, after a business owner confirms the intended outcome.
  None of these repairs is safe to apply in bulk: an employee may have
  resubmitted the leave, a buyer may have raised a replacement PO, or payroll
  may have been re-run.
- Do not replay the module finalizers. Each one refuses to run unless the
  document is still in its pre-decision state (`PENDING` / `APPROVAL`). Use the
  per-module steps below.
- Record every repaired row (who decided, when, and why) in the release
  evidence for the environment.

## 1. Scope the environment

```sql
-- Which modules have policies, and which have engine-approved requests.
SELECT p.module,
       COUNT(DISTINCT p.id)                                  AS policies,
       COUNT(r.id) FILTER (WHERE r.status = 'APPROVED')      AS approved_requests
FROM approval_policies p
LEFT JOIN approval_requests r ON r.policy_id = p.id
GROUP BY p.module
ORDER BY p.module;

-- Steps exposed to the quorum defect (expected: zero rows).
SELECT s.policy_id, s.step_order, s.required_approvals
FROM approval_policy_steps s
WHERE s.required_approvals > 1;
```

The policy form only offers `PO` and `LEAVE`, and nothing seeds
`approval_policies`. If `RFQ_AWARD` or `PAYROLL` has no policies, skip those
sections. If the quorum query returns no rows, skip section 6.

## 2. Leave requests

### Find

```sql
SELECT lr.id                AS leave_request_id,
       e.employee_number,
       lr.leave_type_id,
       lr.start_date,
       lr.end_date,
       lr.days,
       ar.id                AS approval_request_id,
       ar.completed_at,
       (SELECT d.actor_id FROM approval_decisions d
         WHERE d.request_id = ar.id AND d.decision = 'APPROVE'
         ORDER BY d.decided_at DESC LIMIT 1) AS approver_id,
       (SELECT COUNT(*) FROM hr_leave_requests o
         WHERE o.employee_id = lr.employee_id
           AND o.id <> lr.id
           AND o.status IN ('PENDING', 'APPROVED')
           AND daterange(o.start_date, o.end_date, '[]')
               && daterange(lr.start_date, lr.end_date, '[]')) AS overlapping_requests
FROM hr_leave_requests lr
JOIN approval_requests ar ON ar.id = lr.approval_request_id
JOIN hr_employees e ON e.id = lr.employee_id
WHERE lr.status = 'REJECTED'
  AND ar.module = 'LEAVE'
  AND ar.status = 'APPROVED'
ORDER BY lr.start_date;
```

### Decide

- If `overlapping_requests > 0`, the employee already resubmitted. Leave the
  original row `REJECTED`, so the days are not counted twice, and record that
  decision.
- Otherwise, HR confirms whether the leave was taken as approved.

### Repair (one row; replace `:leave_request_id` and `:operator_user_id`)

The balance's `pending` was already released, so only `used` changes. The
balance row is keyed by the year of `start_date`.

```sql
BEGIN;

UPDATE hr_leave_balances b
SET used = b.used + lr.days, updated_at = NOW()
FROM hr_leave_requests lr
WHERE lr.id = :leave_request_id
  AND lr.status = 'REJECTED'
  AND b.employee_id = lr.employee_id
  AND b.leave_type_id = lr.leave_type_id
  AND b.year = EXTRACT(YEAR FROM lr.start_date)::int;   -- expect 1 row

UPDATE hr_leave_requests
SET status = 'APPROVED', updated_at = NOW()
WHERE id = :leave_request_id AND status = 'REJECTED';   -- expect 1 row

INSERT INTO audit_logs (actor_id, action, entity, entity_id, meta)
VALUES (:operator_user_id, 'LEAVE_REMEDIATED', 'hr_leave_request', :leave_request_id::text,
        '{"from":"REJECTED","to":"APPROVED","reason":"approval finalization defect (rc.1-rc.9)"}');

COMMIT;
```

If either UPDATE reports a row count other than 1, `ROLLBACK`. After the
repair, check that `entitled - used - pending` for that balance is not
negative. The employee may have used the "released" days since.

## 3. Purchase orders

### Find

```sql
SELECT p.id                 AS po_id,
       p.number,
       p.supplier_id,
       ar.id                AS approval_request_id,
       ar.requester_id,
       ar.completed_at,
       (SELECT d.actor_id FROM approval_decisions d
         WHERE d.request_id = ar.id AND d.decision = 'APPROVE'
         ORDER BY d.decided_at DESC LIMIT 1) AS final_approver_id,
       (SELECT COUNT(*) FROM pos o
         WHERE o.supplier_id = p.supplier_id
           AND o.id <> p.id
           AND o.created_at > ar.completed_at
           AND o.status <> 'CANCELLED') AS later_pos_same_supplier
FROM pos p
JOIN approval_requests ar ON ar.module = 'PO' AND ar.document_id = p.id
WHERE ar.status = 'APPROVED'
  AND p.status = 'CANCELLED'
ORDER BY ar.completed_at;
```

Every PO approved through the engine on an affected build appears here, unless
someone changed it again afterwards.

### Decide

The buyer decides for each row:

- **Keep cancelled.** A replacement PO exists (`later_pos_same_supplier` is a
  starting point, not proof), or the purchase is no longer needed. No data
  change; record the decision.
- **Restore to approved.** Use the repair below.

### Repair (one row)

```sql
BEGIN;

UPDATE pos p
SET status = 'APPROVED',
    approved_by = :final_approver_id,
    approved_at = ar.completed_at
FROM approval_requests ar
WHERE p.id = :po_id
  AND p.status = 'CANCELLED'
  AND ar.module = 'PO' AND ar.document_id = p.id AND ar.status = 'APPROVED';  -- expect 1 row

INSERT INTO audit_logs (actor_id, action, entity, entity_id, meta)
VALUES (:operator_user_id, 'PO_REMEDIATED', 'po', :po_id::text,
        '{"from":"CANCELLED","to":"APPROVED","reason":"approval finalization defect (rc.1-rc.9)"}');

COMMIT;
```

The false `reject` row in the legacy `approvals` log stays as history. The
audit row above records the correction.

## 4. RFQ awards

### Find

```sql
SELECT aw.id AS award_id, aw.rfq_id, aw.company_id, ar.id AS approval_request_id, ar.completed_at
FROM rfq_awards aw
JOIN approval_requests ar ON ar.module = 'RFQ_AWARD' AND ar.document_id = aw.id
WHERE ar.status = 'APPROVED'
  AND aw.status = 'REJECTED';
```

### Repair

Do not repair these with SQL. An approved award must generate its POs through
`SourcingRepository.GenerateAwardPOs`, under the `rfq-award-po:<award_id>`
idempotency key. Open an engineering ticket for each award: set the award back
to `APPROVAL`, then call `SourcingService.FinalizeApproval` with the APPROVED
request under operator supervision. This approve branch had never run on an
affected build, so verify the generated POs before releasing them.

## 5. Payroll runs

### Find

```sql
SELECT pr.id AS run_id, pr.company_id, pr.period_id, pr.run_type,
       ar.id AS approval_request_id, ar.completed_at
FROM payroll_runs pr
JOIN approval_requests ar ON ar.id = pr.approval_request_id
WHERE ar.module = 'PAYROLL'
  AND ar.status = 'APPROVED'
  AND pr.status = 'APPROVAL';
```

### Repair

There is no HTTP route that posts an approved run. Choose one option for each
run:

- **Post (preferred when the run is still correct).** An engineer calls
  `payroll.Service.Post(runID, approverID)`. First confirm that the company's
  `payroll_account_mappings` are complete and that the accounting period is
  open. Otherwise `Post` fails with `ErrConfiguration` or "no rows".
- **Return to draft and resubmit.** This mirrors `Repository.ResetRejected`:

  ```sql
  BEGIN;
  UPDATE payroll_runs
  SET status = 'DRAFT', approval_request_id = NULL, submitted_at = NULL, updated_at = NOW()
  WHERE id = :run_id AND status = 'APPROVAL';   -- expect 1 row
  INSERT INTO payroll_run_events (run_id, event_type, actor_id, note)
  VALUES (:run_id, 'REJECTED', :operator_user_id,
          'Reset after approval finalization defect (rc.1-rc.9); resubmit for approval');
  COMMIT;
  ```

  The run then goes through approval again on the fixed build.

## 6. Under-quorum decisions (only if section 1 found steps with `required_approvals > 1`)

```sql
SELECT ar.id AS approval_request_id, ar.module, ar.document_id, ar.status,
       s.step_order, s.required_approvals,
       COUNT(a.id) FILTER (WHERE a.status = 'APPROVED') AS approvals
FROM approval_requests ar
JOIN approval_policy_steps s ON s.policy_id = ar.policy_id AND s.required_approvals > 1
JOIN approval_assignments a ON a.request_id = ar.id AND a.policy_step_id = s.id
WHERE ar.status = 'APPROVED' OR s.step_order < ar.current_step
GROUP BY ar.id, ar.module, ar.document_id, ar.status, s.step_order, s.required_approvals
HAVING COUNT(a.id) FILTER (WHERE a.status = 'APPROVED') < s.required_approvals;
```

These requests passed a step with fewer approvals than the policy required.
The document owner decides whether to collect the missing approvals out of
band or to resubmit.

## 7. Multi-step requests waiting on later steps

```sql
SELECT ar.id AS approval_request_id, ar.module, ar.document_id, ar.current_step,
       a.approver_id, a.due_at
FROM approval_requests ar
JOIN approval_assignments a
  ON a.request_id = ar.id AND a.step_order = ar.current_step AND a.status = 'PENDING'
WHERE ar.status = 'PENDING'
  AND ar.current_step > 1;
```

These approvers were never notified on an affected build. No data repair is
needed. Tell them directly, or wait for the next escalation re-alert.

## Verification after deploy

- `go test ./internal/approvals` covers final approval, advance, an
  unsatisfied quorum and rejection against the repository SQL.
- `TestStagingHRCoreJourney` (see
  [`approvals-hr-core.md`](../guides/approvals-hr-core.md#end-to-end-scenario))
  approves a leave request end to end. Step 7 fails on affected builds and
  passes on the fixed build. It depends on HR routes that are not in
  v0.10-core, so it is not part of the rc.10 candidate.
- Re-run the **Find** queries above. Once the fix is deployed, rows from
  decisions made after the deploy must not appear.

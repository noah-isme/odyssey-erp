# v0.10-core Operator Lane Prerequisites

**Purpose:** everything the operator needs before the operator evidence lane
(11 contract rows: `ENV-001`, `DB-001`, `DB-003`, `DB-004`, `OPS-001`–`OPS-005`,
`ISO-004`, `APR-001`) can be executed. The automated lane cannot close these rows.

**Candidate:** tag `v0.10.0-rc.8` → `20cc13a0f028e3b09573944bb9f7a1f943461253`,
profile `v0.10-core`, ceiling `000124`.

## 2. Artifact prerequisites (must exist before the lane starts)

- [ ] Previous verified staging release directory under `/opt/odyssey-staging/releases/` (rollback target for OPS-004). If only one release exists, the rollback exercise cannot run — deploy the prior bundle first or document the gap.
- [ ] Sanitized backup of a production-like dataset, with source identity, redaction record, and checksum (DB-001).
- [ ] Two empty scratch databases for clean-restore exercises (DB-003 down/up rehearsal, DB-004 clean restore).
- [ ] Storage location (host path) for raw operator logs/screenshots before they are uploaded to the immutable evidence store.
- [ ] Monitoring dashboard or log-based metrics source capable of producing the 60-minute observation record (OPS-005): UTC start/end, request error rate, latency, queue depth, DB/Redis health, resource saturation, alerts, incidents, handoff owner.

## 3. Safety constraints (operator rules)

1. Staging only — no production host, credential, DSN, or dataset.
2. Never run an untested down migration against the live staging database; the `000124` down/up rehearsal runs on a disposable clone only (DB-003).
3. Rollback exercise (OPS-004) switches the app symlink only; database rollback is a separate documented decision.
4. Every row requires raw output capture; narrative-only evidence is rejected by closeout validation.
5. Any failed row stays `FAIL`; it is never edited to `PASS` — the run is repeated after correction.

## 4. Execution order (once prerequisites and automated lane exist)

1. ENV-001 environment identity capture (host, DB, Redis, storage, secrets, filesystem, systemd).
2. DB-001 sanitized restore + integrity checks (before any migration work).
3. DB-004 pre-deploy backup → checksum → clean-DB restore → connectivity.
4. DB-003 disposable-clone `000124` down/up + checksums + irreversibility notes.
5. OPS-001 health/services/digests/logs.
6. OPS-002 cookies/CSRF/session/TLS/secret boundary.
7. OPS-003 queue delivery/retry/dead-letter + audit + alerts. Known worker
   findings not fixed in rc.9 are pre-recorded as `FIND-001`–`FIND-008` in the
   [certification record findings](v0.10-core-staging-certification.md#findings)
   (CRM reminder race, overdue-invoice recipient, mail payload trust, BI export,
   connector outbox and payslip at-least-once windows, CMMS PM scan overlap,
   finance automation dispatch); attach their reproductions here instead of
   raising duplicates.
8. ISO-004 forged/retried worker inputs (needs prerequisite #8 procedure).
9. OPS-004 rollback to previous bundle → health → restore rc.8 → digest re-verified.
10. OPS-005 60-minute observation window (starts only after the final restore in step 9).
11. APR-001 approval packet assembly (after all rows PASS).

## 6. OPS-005 observation collector

`scripts/staging-certification-observe.sh` produces the raw OPS-005 record. It is
read-only against the staging host (health GET, journal and `systemctl show` reads,
Redis `PING`/`LLEN`/`ZCARD`/`EXISTS`, `pg_isready`, `df`, `/proc`) and redacts every
captured text. Start it from `tmux` after the OPS-004 final restore, as a user who can
read the journal and `/opt/odyssey-staging/.env` (or pass `--pg-check-cmd` and export
`REDIS_ADDR`). Create the alerts and incidents files first; they are read at the end
of the window, so write to them while it runs.

```bash
scripts/staging-certification-observe.sh --confirm-staging \
  --out /var/lib/odyssey-evidence/ops-005 --handoff-owner "<name>" \
  --candidate-tag v0.10.0-rc.8 --expected-sha 20cc13a0f028e3b09573944bb9f7a1f943461253 \
  --alerts-file ops-005-alerts.txt --incidents-file ops-005-incidents.txt
```

Rehearse first with `--rehearsal --duration 300`; a rehearsal is always
`eligible_for_ops005: false`, as is any interrupted run. The output directory holds
`samples.jsonl` (one object per sample), `summary.json`, `raw/<NNNN>/` captures, and a
`SHA256SUMS` that verifies with `sha256sum -c`. The summary reports observations and
`anomalies` only. The reviewer decides `PASS` or `FAIL`, and alerts or incidents that
were not supplied read `not supplied`, never none. Request error rate and latency come
from the app's chi access log in the journal; there is no `/metrics` endpoint, and the
collector's own `/healthz` probes appear in those counts (reported separately as
`requests_healthz`).

To register the row, copy the directory into the operator candidate directory as
`ops-005-observation/` and append one reviewed record to its
`staging-certification.log`, then run `staging-certification-evidence.sh --lane operator`:

```text
CERTIFICATION_EVIDENCE evidence_id=OPS-005 {"evidence_id":"OPS-005","result":"<PASS|FAIL>","collected_utc":"<summary utc_end>","details":"ops-005-observation/summary.json reviewed by <name>"}
```

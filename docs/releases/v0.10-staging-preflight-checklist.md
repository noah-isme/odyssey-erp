# v0.10-core Staging Preflight Checklist

**Purpose:** enumerate every input the certification workflow requires before
`certify-v010-staging.yml` can be dispatched. The workflow fails closed on any
missing item — this checklist is the provisioning contract.

**Candidate:** annotated tag `v0.10.0-rc.11` → `<short-sha>` (recorded when the
tag is cut), profile `v0.10-core`, migration ceiling `000124`; lineage is the
superseded rc.10 tag `0745957` plus the rc.11 fix commits; no migration.
**Dispatch branch:** `certification/v0.10.0-rc.11` (created from the rc.11 tag
after it is cut; not yet on origin).
**Environment:** GitHub `staging` (currently 3 secrets, 0 variables).

## 0. Prerequisite: staging rebuilt from an empty database

Staging still holds rows fabricated by the invalidated rc.10 run (`FIND-009`,
`FIND-020`), so the rc.11 certification may not be dispatched against it.
Before the rc.11 tag is pushed (the tag push deploys staging), the operator
performs the rebuild from the rc.11 checkout, after written user approval
(Step 19 of the rc.11 plan; runbook `v0.10-rc11-staging-rebuild.md`, added with that step):

- [ ] written approval recorded (URL and date) in the certification record
- [ ] both staging units stopped; forensic `pg_dump -Fc` of the old database
      and its `sha256sum` uploaded to the evidence bucket under
      `v0.10.0-rc.10/forensics/<UTC timestamp>/` (never under the rc.11
      prefix); object key and SHA-256 recorded in `FIND-010`
- [ ] database dropped and recreated (same name, owner, encoding, locale),
      `btree_gist` extension created, dedicated staging Redis DB flushed (or,
      if shared, the session, CSRF and asynq prefixes deleted and recorded)
- [ ] `migrate up` from the rc.11 checkout; `schema_migrations` max `124`,
      `dirty = false`
- [ ] least-privileged certification role re-granted (`CONNECT`, `USAGE` on
      `public`, `SELECT` on all tables, default privileges); `SELECT` works and
      `INSERT` is refused with that role
- [ ] schema checksum (section E) equal to a fresh PG17 reference
- [ ] every `STAGING_CERT_*` password rotated and the GitHub secrets updated
      before seeding (the forensic dump holds the old hashes)
- [ ] `go run ./scripts/seed/staging` (base seeder, then ISO-004 fixtures) run
      with the new identities; `cmd/bootstrap-admin` is **never** run for the
      certification identity (it would add an assignment in the other company
      and break ISO-002)
- [ ] `SELECT count(*)` of `journals`, `ar_invoices`, `ap_invoices`,
      `documents`, `work_orders` was 0 before the seed and only seed rows after

- [ ] role 1 review: migration `000083` grants `cmms.%`, `qms.%` and `documents.%` to `role_id = 1`, which is `Sales Manager` on a migrations-only database (`FIND-022`). The staging seeder revokes those grants while role 1 is not named admin/administrator and prints what it removed. Other environments run this read-only review query and decide with the release owner:

  ```sql
  SELECT r.id, r.name, p.name AS permission
  FROM role_permissions rp
  JOIN roles r ON r.id = rp.role_id
  JOIN permissions p ON p.id = rp.permission_id
  WHERE rp.role_id = 1
    AND LOWER(TRIM(r.name)) NOT IN ('admin', 'administrator')
    AND (p.name LIKE 'cmms.%' OR p.name LIKE 'qms.%' OR p.name LIKE 'documents.%')
  ORDER BY p.name;
  ```

## E. Schema checksum prerequisites (DB-002)

The `Schema checksum gate` step of `certify-v010-staging.yml` runs
`scripts/staging-schema-checksum.sh` before any test and aborts the dispatch
when the staging schema differs from a fresh reference migrated with the
bundle's migrations.

- [ ] staging PostgreSQL is major version 17: the `pg_dump` client, the
      reference server (the workflow's `postgres:17` service) and staging must
      share one major, and the script refuses otherwise (PG15's `pg_dump`
      qualifies view columns differently). The workflow installs
      `postgresql-client-17` from PGDG; a local run without a PG17 client sets
      `PG_DUMP_CMD`/`PSQL_CMD` to a `postgres:17` container's tools
- [ ] `STAGING_CERT_PG_DSN` can `SELECT` every table in `public` (the dump and
      the ceiling check read only; sessions are read-only)
- [ ] staging `schema_migrations` reads exactly `124`, `dirty = false`
- [ ] a local dry run after the rebuild (section 0) matched, with
      `reference.sql`, `staging.sql`, `schema.diff` and `schema-checksum.txt`
      kept as operator evidence

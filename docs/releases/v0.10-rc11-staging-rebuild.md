# v0.10.0-rc.11 staging rebuild runbook (destructive)

**Status:** procedure only. Nothing in this document has been run. It
implements Step 19 of the rc.11 plan and closes the rebuild half of `FIND-020`
and the forensic-dump half of `FIND-010` in the
[certification record](v0.10-core-staging-certification.md).

**What it does:** wipes the staging database (fabricated rows left by the
invalidated rc.10 certification run, `FIND-009`, `FIND-010`, `FIND-020`),
rebuilds it from migrations `000001`-`000124`, re-creates the certification
role grants and identities, seeds the certification fixtures, and prepares the
host for the first rc.11 deploy. It also covers the per-dispatch seeder re-run.

### Session secrets

Load every DSN and password into the shell with prompts (nothing is echoed or
written to history), and keep database passwords out of the DSNs and out of
process arguments with a private password file. `psql`, `pg_dump`, `migrate`
and the seeder all read `PGPASSFILE`:

```bash
umask 077
export PGPASSFILE="$(mktemp)"            # one line per role: host:port:database:user:password
"${EDITOR:-vi}" "$PGPASSFILE"           # paste the lines from the secret store; never commit or print this file
read -rs -p 'ADMIN_DSN (no password): ' ADMIN_DSN && echo && export ADMIN_DSN
read -rs -p 'OWNER_DSN (no password): ' OWNER_DSN && echo && export OWNER_DSN
read -rs -p 'CERT_DSN (no password): '  CERT_DSN  && echo && export CERT_DSN
read -rs -p 'REDIS_ADDR: '              REDIS_ADDR && echo && export REDIS_ADDR
```

The DSNs above carry no password, so expanding them on a command line exposes
no secret. Remove the password file at the end of the session
(`shred -u "$PGPASSFILE"`).

Confirm the role behind `$ADMIN_DSN` can recreate the database **before**
anything is dropped (section 3 drops `<db>` and re-creates it with
`OWNER "<owner-role>"`). On PostgreSQL 16 and later (staging runs 17),
`CREATE DATABASE ... OWNER` requires being able to `SET ROLE` to the owner
(the `SET` option of the role grant) and `DROP DATABASE` requires the owner's
privileges (membership with `INHERIT`, tested as `USAGE`):

```bash
psql "$ADMIN_DSN" -X -A -t -c "SELECT rolsuper, rolcreatedb, pg_has_role(current_user, '<owner-role>', 'SET'), pg_has_role(current_user, '<owner-role>', 'USAGE') FROM pg_roles WHERE rolname = current_user"
# expected: f|t|t|t, or t in the first column (a superuser; pg_has_role is then
# always t and rolcreatedb does not matter)
# anything else: STOP. For example f|t|f|t (granted WITH SET FALSE) can drop
# the database but CREATE DATABASE then fails with
# 'must be able to SET ROLE "<owner-role>"', leaving staging without a database.
```

On a server older than PostgreSQL 16 the `SET` option does not exist and
`pg_has_role(..., 'SET')` raises an error; use `'MEMBER'` in its place
(any member may `SET ROLE` there) and keep the `USAGE` column. Verified on
`postgres:17` with a `CREATEDB` role granted the owner role `WITH SET TRUE`
(`f|t|t|t`, create and drop succeed) and `WITH SET FALSE` (`f|t|f|t`,
`CREATE DATABASE` refused).

Confirm the `btree_gist` extension package exists on the **PG17 host** before
dropping anything. Migration `000047` needs it and a missing package would
leave staging without a database.

```bash
psql "$ADMIN_DSN" -X -A -t -c "SELECT name, default_version FROM pg_available_extensions WHERE name = 'btree_gist'"
# expected: btree_gist|1.7   (any version; an empty result means STOP and install
# the postgresql-17 contrib package on the database host first)
```

Confirm the `postgres:17` image or server for the checksum reference is
available (section 6).

## 2. Forensic dump (evidence, not a restore point)

The dump preserves the invalidated run's database as the reproduction artifact
for `FIND-009` and `FIND-010`.

```bash
export STAMP=$(date -u +%Y%m%dT%H%M%SZ)
export DUMP=forensic-<db>-$STAMP.dump

pg_dump -Fc --no-password --dbname="$OWNER_DSN" --file="$DUMP"
test -s "$DUMP" && ls -l "$DUMP"
pg_restore --list "$DUMP" | head -5          # must list a TOC; proves the file is readable
sha256sum "$DUMP" | tee "$DUMP.sha256"
# expected: <64 hex characters>  forensic-<db>-<STAMP>.dump
```

Upload under the **rc.10 forensics prefix**, with Object Lock COMPLIANCE like
the rest of the bucket (seven years; the bucket default retention also
applies):

```bash
export KEY="v0.10.0-rc.10/forensics/$STAMP/$DUMP"
RETAIN_UNTIL=$(date -u -d '+7 years' +%Y-%m-%dT%H:%M:%SZ)

aws s3api put-object --endpoint-url <R2-endpoint> --bucket <bucket> \
  --key "$KEY" --body "$DUMP" \
  --object-lock-mode COMPLIANCE --object-lock-retain-until-date "$RETAIN_UNTIL" \
  --metadata "sha256=$(cut -d' ' -f1 "$DUMP.sha256")"
aws s3api put-object --endpoint-url <R2-endpoint> --bucket <bucket> \
  --key "$KEY.sha256" --body "$DUMP.sha256" \
  --object-lock-mode COMPLIANCE --object-lock-retain-until-date "$RETAIN_UNTIL"

aws s3api head-object --endpoint-url <R2-endpoint> --bucket <bucket> --key "$KEY" \
  --query '{Mode:ObjectLockMode,Until:ObjectLockRetainUntilDate,Size:ContentLength,Meta:Metadata}'
# expected: Mode COMPLIANCE, Until about seven years out, Size equal to the local file, Meta.sha256 equal to the local digest
```

Round-trip check (the lock makes a bad upload permanent, so verify):

```bash
aws s3 cp --endpoint-url <R2-endpoint> "s3://<bucket>/$KEY" - | sha256sum
# expected: the same 64 hex characters as in $DUMP.sha256
```

Rules:

- The key must start with `v0.10.0-rc.10/forensics/`. It must **never** be under
  the rc.11 evidence prefix `v0.10.0-rc.11/<sha>/...`, and it must not appear
  in any rc.11 evidence index. The certification evidence validator
  (`scripts/staging-certification-evidence.sh`) must not list it; confirm after
  every dispatch that the index contains no `forensics/` key.
- The dump contains the **old bcrypt password hashes** of the certification
  identities and cannot be deleted for seven years. That is why section 7
  rotates the passwords before seeding.
- Keep the local dump on an encrypted volume until the upload is verified, then
  shred it: `shred -u "$DUMP"` (the `.sha256` file may be kept).

Record in `FIND-010`: the object key `$KEY` and the SHA-256, replacing the
`<v0.10.0-rc.10/forensics/<UTC timestamp>/...>` and `<64-hex SHA-256>`
placeholders.

## 3. Drop and recreate the database; flush Redis

Capture the current database properties **before** dropping, and keep the
output with the evidence:

```bash
psql "$ADMIN_DSN" -X -A -F '|' -c "
SELECT d.datname,
       pg_catalog.pg_get_userbyid(d.datdba)      AS owner,
       pg_catalog.pg_encoding_to_char(d.encoding) AS encoding,
       d.datlocprovider, d.datcollate, d.datctype, d.datlocale,
       d.datconnlimit,
       (SELECT spcname FROM pg_catalog.pg_tablespace t WHERE t.oid = d.dattablespace) AS tablespace
FROM pg_catalog.pg_database d WHERE d.datname = '<db>'"
psql "$OWNER_DSN" -X -A -t -c "SELECT extname FROM pg_extension ORDER BY extname"
```

The second command lists the extensions in the old database (run against
`$OWNER_DSN`, which still points at the old database at this point). Only
`btree_gist` is required by the migrations; if anything else is listed, decide
explicitly whether the rebuilt database needs it.

Recreate with the captured values. Example for a `libc` provider; if
`datlocprovider` is `i` (ICU) use `LOCALE_PROVIDER icu ICU_LOCALE '<datlocale>'`
instead of `LC_COLLATE`/`LC_CTYPE`:

```bash
psql "$ADMIN_DSN" -X -v ON_ERROR_STOP=1 <<'SQL'
DROP DATABASE "<db>" WITH (FORCE);
CREATE DATABASE "<db>"
  OWNER "<owner-role>"
  TEMPLATE template0
  ENCODING '<encoding>'
  LC_COLLATE '<datcollate>'
  LC_CTYPE '<datctype>'
  CONNECTION LIMIT <datconnlimit>;
SQL
```

Create the extension that migration `000047` needs. `CREATE EXTENSION
btree_gist` requires superuser, or a trusted-extension-capable owner on PG13+
(`btree_gist` is trusted):

```bash
psql "$OWNER_DSN" -X -v ON_ERROR_STOP=1 -c "CREATE EXTENSION IF NOT EXISTS btree_gist"
psql "$OWNER_DSN" -X -A -t -c "SELECT extname FROM pg_extension ORDER BY extname"
# expected: btree_gist and plpgsql
psql "$OWNER_DSN" -X -A -t -c "SELECT count(*) FROM pg_tables WHERE schemaname = 'public'"
# expected: 0
```

### Redis

`REDIS_ADDR` is either `host:port` or a `redis://` / `rediss://` URL
(`internal/platform/cache/redis.go`, `redisOptions`): a URL may carry a
username, password, TLS (`rediss://`) and a database number (`/<n>`), and the
web process, the session store and asynq all use that database; a plain
`host:port` uses database 0. Sessions are stored as `session:<id>` (the CSRF
token lives inside the session), queues under `asynq:`. User ids restart in
the new database, so no session or task from the old database may survive.

Define one `redis-cli` wrapper for the form in use (`REDIS_ADDR` comes from
"Session secrets"; with a URL, `redis-cli -u` selects the URL's database, so
do not add `-n`):

```bash
case "$REDIS_ADDR" in
  rediss://*) rcli() { redis-cli -u "$REDIS_ADDR" --tls "$@"; } ;;
  redis://*)  rcli() { redis-cli -u "$REDIS_ADDR" "$@"; } ;;
  *)          rcli() { redis-cli -h "${REDIS_ADDR%:*}" -p "${REDIS_ADDR##*:}" -n 0 "$@"; } ;;
esac
rcli PING      # expected: PONG
```

`redis-cli -u` puts a URL password on its command line (visible to local
`ps`); if the URL carries a password, run this from a workstation session that
is not shared, or move the password to `REDISCLI_AUTH` and drop it from the
URL for these commands.

Check what the database holds and whether it is dedicated to staging:

```bash
rcli DBSIZE
rcli INFO keyspace
rcli --scan --pattern '*' | sed -E 's/^([^:]+):.*/\1/' | sort | uniq -c
# a dedicated staging Redis database shows only: session, asynq (and nothing foreign)
```

**Variant A, dedicated staging Redis database** (nothing else uses it):

```bash
rcli FLUSHDB
rcli DBSIZE
# expected: (integer) 0
```

**Variant B, shared Redis database** (anything foreign appears above): delete
only the application prefixes and record which ran and the counts removed.

```bash
for pat in 'session:*' 'asynq:*'; do
  rcli --scan --pattern "$pat" | while read -r key; do rcli DEL "$key" >/dev/null; done
done
```

Verify after either variant (both must print 0, and the prefix scan must list
no `session` or `asynq` line):

```bash
rcli --scan --pattern 'session:*' | wc -l   # expected 0
rcli --scan --pattern 'asynq:*'  | wc -l    # expected 0
rcli --scan --pattern '*' | sed -E 's/^([^:]+):.*/\1/' | sort | uniq -c
rcli DBSIZE                                  # Variant A: (integer) 0
```

If the scan above showed any other application prefix that holds session or
CSRF state (for example a `csrf` prefix), delete it in the same way and list it
in the record. Record "Variant A" or "Variant B", the Redis database (`0` for
`host:port`, or the URL's database number) and the prefixes.

## 5. Re-grant the least-privileged certification role

`DROP DATABASE` removed every grant the role held. Re-grant **before** the
checksum (section 6) uses `STAGING_CERT_PG_DSN`. Run as the database owner:

```bash
psql "$OWNER_DSN" -X -v ON_ERROR_STOP=1 <<'SQL'
GRANT CONNECT ON DATABASE "<db>" TO "<cert-role>";
GRANT USAGE ON SCHEMA public TO "<cert-role>";
GRANT SELECT ON ALL TABLES IN SCHEMA public TO "<cert-role>";
ALTER DEFAULT PRIVILEGES FOR ROLE "<owner-role>" IN SCHEMA public
  GRANT SELECT ON TABLES TO "<cert-role>";
SQL
```

`FOR ROLE "<owner-role>"` is the role that creates tables (the migration
user); default privileges apply only to objects created by that role. The
role gets no `INSERT`, `UPDATE`, `DELETE`, `CREATE` or sequence privileges.

Verify with the certification role:

```bash
psql "$CERT_DSN" -X -A -t -c "SELECT count(*) FROM journal_entries"
# expected: 0

psql "$CERT_DSN" -X -v ON_ERROR_STOP=1 -c "INSERT INTO journal_entries DEFAULT VALUES"
echo "exit=$?"
# expected: ERROR:  permission denied for table journal_entries
#           exit=1

psql "$CERT_DSN" -X -A -t -c "SELECT count(*) FROM information_schema.tables t WHERE table_schema='public' AND table_type='BASE TABLE' AND NOT has_table_privilege(current_user, format('%I.%I', table_schema, table_name), 'SELECT')"
# expected: 0   (every table is readable)
```

A table-by-table `SELECT` succeeding and the `INSERT` refusal are both
required; paste the outputs into the record.

## 6. Schema checksum against a fresh PG17 reference

`scripts/staging-schema-checksum.sh` migrates a fresh, empty reference
database with the checkout's migrations, dumps both schemas with a PG17
`pg_dump`, normalises and compares SHA-256 digests. It only reads staging (in
read-only sessions) and refuses a reference database that already has
`schema_migrations`. It requires staging `schema_migrations` to read exactly
`124`, clean (section 4).

Create a throwaway reference server and database. Either a PG17 container:

```bash
read -rs -p 'throwaway reference password: ' POSTGRES_PASSWORD && echo && export POSTGRES_PASSWORD
docker run -d --name rc11-ref-pg17 -e POSTGRES_PASSWORD -p 127.0.0.1:<ref-port>:5432 postgres:17
# wait for readiness
until docker exec rc11-ref-pg17 pg_isready -U postgres; do sleep 1; done
printf '127.0.0.1:<ref-port>:*:postgres:%s\n' "$POSTGRES_PASSWORD" >> "$PGPASSFILE"
export REF_ADMIN_DSN='postgres://postgres@127.0.0.1:<ref-port>/postgres?sslmode=disable'
export REF_DSN='postgres://postgres@127.0.0.1:<ref-port>/odyssey_ref?sslmode=disable'
psql "$REF_ADMIN_DSN" -X -v ON_ERROR_STOP=1 -c "CREATE DATABASE odyssey_ref"
psql "$REF_DSN" -X -v ON_ERROR_STOP=1 -c "CREATE EXTENSION IF NOT EXISTS btree_gist"
```

or any other empty PG17 database. The reference needs `btree_gist` too.

Run the gate with the **read-only certification DSN**:

```bash
mkdir -p rebuild-evidence/schema-checksum-rebuild
scripts/staging-schema-checksum.sh \
  --staging-dsn "$CERT_DSN" \
  --reference-dsn "$REF_DSN" \
  --migrations migrations \
  --ceiling 124 \
  --out rebuild-evidence/schema-checksum-rebuild
echo "exit=$?"
```

If the workstation has no PG17 client, set the tool overrides (see the script
header), for example, as in the script header:

```bash
export PG_DUMP_CMD='docker run --rm -i --network host -e PGOPTIONS postgres:17 pg_dump'
```

Keep `-e PGOPTIONS`: the script sets
`PGOPTIONS='-c default_transaction_read_only=on'` for every staging session,
and without forwarding it the containerised `pg_dump` would not run in a
read-only session. With a containerised client the password file must be
reachable inside the container too (for example add
`-e PGPASSFILE=/pgpass -v "$PGPASSFILE":/pgpass:ro`).

Expected output:

```text
pg_dump client major 17, staging server 17.x, reference server 17.x
reference sha256 <64 hex>
staging   sha256 <64 hex>      # identical to the line above
schema checksum gate passed (migration ceiling 124)
exit=0
```

`rebuild-evidence/schema-checksum-rebuild/schema-checksum.txt` must read
`result=MATCH` with equal `reference_sha256` and `staging_sha256`. Keep
`reference.sql`, `staging.sql`, `schema.diff` (empty) and the txt as evidence.
On `exit=1` read `schema.diff`; do not proceed to seeding until it is
explained (a difference after a clean `migrate up` means the checkout, the
extension set or the PG major differs from what is assumed here). Remove the
reference container afterwards: `docker rm -f rc11-ref-pg17`.

## 7. Rotate passwords, then seed

### 7.1 Rotate every certification password first

Rotate `STAGING_CERT_ADMIN_PASSWORD`, `STAGING_CERT_BRANCH_PASSWORD` and
`STAGING_CERT_NO_ACCESS_PASSWORD`. The forensic dump (section 2) holds the old
bcrypt hashes under a compliance lock for seven years, so the old values must
be dead before the new database ever stores a hash.

```bash
export STAGING_CERT_ADMIN_PASSWORD=$(openssl rand -base64 33)
export STAGING_CERT_BRANCH_PASSWORD=$(openssl rand -base64 33)
export STAGING_CERT_NO_ACCESS_PASSWORD=$(openssl rand -base64 33)

printf '%s' "$STAGING_CERT_ADMIN_PASSWORD"     | gh secret set STAGING_CERT_ADMIN_PASSWORD     --env staging
printf '%s' "$STAGING_CERT_BRANCH_PASSWORD"    | gh secret set STAGING_CERT_BRANCH_PASSWORD    --env staging
printf '%s' "$STAGING_CERT_NO_ACCESS_PASSWORD" | gh secret set STAGING_CERT_NO_ACCESS_PASSWORD --env staging
gh secret list --env staging | grep -E 'STAGING_CERT_(ADMIN|BRANCH|NO_ACCESS)_PASSWORD'
# expected: three rows with a fresh updated timestamp
```

Also set (or confirm) the three email secrets/variables
`STAGING_CERT_ADMIN_EMAIL`, `STAGING_CERT_BRANCH_EMAIL`,
`STAGING_CERT_NO_ACCESS_EMAIL` and export the same values for the seeder. **Do
not rely on the seeder defaults**: if the password variables are unset the
seeder falls back to the well-known development passwords (`admin123`,
`branch123`, `noaccess123`) from `scripts/seed/staging/base_seed.go`.

### 7.3 Preview, then seed the base fixtures

The seeder is guarded: it needs an explicit DSN, `APP_ENV=staging`,
`--confirm-staging <db>@<db-host>` matching the DSN host and database and
`current_database()`, and it refuses a host matching `prod`
(`--deny-host-regex`). It runs as the **owner** role.

```bash
export APP_ENV=staging
export PG_DSN="$OWNER_DSN"       # the seeder reads PG_DSN; the password comes from PGPASSFILE
export STAGING_CERT_ADMIN_EMAIL='<admin-email>'
export STAGING_CERT_BRANCH_EMAIL='<branch-email>'
export STAGING_CERT_NO_ACCESS_EMAIL='<no-access-email>'
# the three *_PASSWORD variables are already exported from 7.1

# 1) --check: every step in a rolled-back transaction, nothing committed
go run ./scripts/seed/staging --confirm-staging <db>@<db-host> --check
echo "exit=$?"
# expected on an empty database: a long list of "missing" rows and exit=1 (this
# is the normal result before the first seed; sequences advance, which is
# harmless because ids are only read from the real run)

# 2) the real run
go run ./scripts/seed/staging --confirm-staging <db>@<db-host> \
  --json > rebuild-evidence/base-fixtures.json 2> rebuild-evidence/base-seed-report.txt
echo "exit=$?"     # expected 0
```

The stderr report starts with `Base seeder on <db>@<db-host>: N created, M
reused` and then one line per row. `M` covers only rows that migrations already
created (such as `role_admin` and possibly permissions); read every `reused`
line and confirm it is a migration-owned row. Expect these rows, `created`
unless noted:

- users: `user_admin`, `user_branch`, `user_no_access`; `role_admin` (the
  seeder reuses an existing `admin` role, and migrations normally create it, so
  this line is usually `reused`; the "0 reused" statement below applies to all
  other rows) and `user_admin_role` in `user_roles`
- `company_primary`, `company_other`, `branch_primary`, `branch_other`,
  `warehouse_primary`, `unit`, `category`, `product`, `inventory_balance`
- `customer_primary`, `supplier_primary`, `customer_other`, `ar_invoice_other`
  (the other company's invoice that ISO-002 reads)
- RBAC: `rbac_assignment_admin` (one company-wide assignment in the primary
  company), `role_branch_user`, `rbac_assignment_branch`,
  `rbac_assignment_expired`, `rbac_access_review_revoke`
- `permission <name>` and `admin permission <name>` rows for the enumerated
  admin set; the line `Admin role granted N permission(s): ...`
- documents: `document_numbering_rule`, `document_classification`,
  `document_category`, `retention_policy`
- reviewed tax configuration: `tax_rule_version_vat` (rule version
  `STG-CERT-VAT-V010`), `tax_code VAT_OUTPUT`, `tax_code VAT_INPUT`,
  `company_tax_identity_primary`, `account 2110`, `account 1410`,
  `tax_account_mapping ...` (accounts `2110` and `1410`),
  `tax_invoice_number_range_primary`, and the `tax_id` on the base customer and
  supplier
- ledger prerequisites: `account <code>` and `mapping <module>/<key>` rows,
  `period_open_today` (an OPEN period covering today) and
  `accounting_period_open_today` (the linked `accounting_periods` row)
- AP: `ap_matching_policy` (a zero-tolerance policy scoped to the base
  supplier: `supplier_id` set, `company_id` NULL; never a global policy, which
  the ISO-004 guard refuses)
- P2P: `po_primary` and `grn_primary` (a PO with a goods receipt that has not
  been invoiced)
- trailing lines: `Role 1 cmms/qms/documents grants revoked: none` and
  `Certification GRN: fresh grn id=<n> (po id=<n>); update STAGING_CERT_GRN_ID=<n> before the next dispatch`

A `reused` user, branch, company, customer, supplier, GRN or tax row, a
`refusing ...` error, or a non-empty revoked list on a freshly created
database means the database was not empty: stop and investigate. The base seeder never modifies existing users and refuses an
existing user with a different password.

### 7.4 ISO-004 fixtures

Choose a run key that matches `^[A-Za-z0-9][A-Za-z0-9-]{0,39}$` (no dots). The
same key is passed as `--run-id` to `scripts/certification/iso004` later, so
use the one the ISO-004 procedure assigns
([ISO-004 procedure](v0.10-iso004-worker-injection-procedure.md)).

```bash
export ISO004_KEY='<run-key>'

go run ./scripts/seed/staging --iso004 --iso004-key "$ISO004_KEY" \
  --confirm-staging <db>@<db-host> --dry-run
# expected: guard passes; planned inserts listed as would-insert; nothing written

go run ./scripts/seed/staging --iso004 --iso004-key "$ISO004_KEY" \
  --confirm-staging <db>@<db-host> --json > rebuild-evidence/iso004-fixtures.json
echo "exit=$?"     # expected 0
```

### 7.5 Never use `cmd/bootstrap-admin` for this identity

Do **not** run `cmd/bootstrap-admin` (or the dev seed) for the certification
admin, on this database or later:

- it grants no `documents` or CMMS permissions, so the journeys that need them
  would fail with `403`;
- with rc.11's company scoping it creates company-wide assignments for every
  company, which adds an assignment in the other company and breaks `ISO-002`
  (the admin must have exactly one active assignment, in the primary company);
- the seeder is the only writer of the certification identities, and
  `RBAC_GLOBAL_ROLES` stays empty.

Check after seeding:

```bash
psql "$CERT_DSN" -X -A -t -c "
SELECT count(*) FROM rbac_user_role_assignments a JOIN users u ON u.id = a.user_id
WHERE u.email = '<admin-email>' AND a.valid_from <= NOW() AND (a.valid_to IS NULL OR a.valid_to > NOW())"
# expected: 1
```

### 7.6 Counts after the seed

Repeat the query from 7.2. The counts are no longer necessarily 0: the base
seeder creates the other company's AR invoice (`ar_invoice_other`) and the
ISO-004 seed creates its own AP invoices, documents and related rows. Every
row must be traceable to a line in `base-seed-report.txt` or the ISO-004
output (`iso004-fixtures.json`). An unexplained row means something other than
the seeder wrote to the database.

## 8. Fixture ids into GitHub and `.env`

`rebuild-evidence/base-fixtures.json` holds the twelve fixture values. Update
**every** one in the GitHub `staging` environment (the preflight fails closed
on a stale id):

```bash
for name in STAGING_CERT_COMPANY_ID STAGING_CERT_BRANCH_ID \
            STAGING_CERT_OTHER_COMPANY_ID STAGING_CERT_OTHER_BRANCH_ID \
            STAGING_CERT_CUSTOMER_ID STAGING_CERT_SUPPLIER_ID \
            STAGING_CERT_PRODUCT_ID STAGING_CERT_WAREHOUSE_ID \
            STAGING_CERT_GRN_ID STAGING_CERT_DOCUMENT_CATEGORY_ID \
            STAGING_CERT_DOCUMENT_CLASSIFICATION_ID STAGING_CERT_AMOUNT; do
  value=$(jq -r --arg n "$name" '.[$n]' rebuild-evidence/base-fixtures.json)
  gh variable set "$name" --env staging --body "$value"
done
gh variable list --env staging
```

(`--apply-gh` on the seeder does the same; the loop above is explicit and
reviewable.) Also set the ISO-004 variables from `iso004-fixtures.json` as the
[ISO-004 procedure](v0.10-iso004-worker-injection-procedure.md) and the
[preflight checklist](v0.10-staging-preflight-checklist.md) section B require.

Resolve each id back to a seeded row owned by the recorded company:

```bash
psql "$CERT_DSN" -X -A -t -c "
SELECT 'branch',    count(*) FROM branches   WHERE id = <branch-id>    AND company_id = <company-id> UNION ALL
SELECT 'warehouse', count(*) FROM warehouses w JOIN branches b ON b.id = w.branch_id WHERE w.id = <warehouse-id> AND b.company_id = <company-id> UNION ALL
SELECT 'customer',  count(*) FROM customers  WHERE id = <customer-id>  AND company_id = <company-id> UNION ALL
SELECT 'supplier',  count(*) FROM suppliers  WHERE id = <supplier-id>  AND company_id = <company-id> UNION ALL
SELECT 'grn',       count(*) FROM grns       WHERE id = <grn-id>       AND company_id = <company-id>"
# expected: every row has count 1 (also confirm the GRN is the id printed on
# the "Certification GRN" line)
```

Set `CMMS_SYSTEM_USER_ID` to the seeded admin's `users.id` (the `user_admin`
line in `base-seed-report.txt`) in `/opt/odyssey-staging/.env` on the host:

```bash
ADMIN_ID=$(psql "$CERT_DSN" -X -A -t -c "SELECT id FROM users WHERE email = '<admin-email>'")
echo "$ADMIN_ID"          # expected: the id on the user_admin line of base-seed-report.txt (not
                          # necessarily 1: the --check run in 7.3 advanced the sequences)
sudo sed -i "s/^CMMS_SYSTEM_USER_ID=.*/CMMS_SYSTEM_USER_ID=$ADMIN_ID/" /opt/odyssey-staging/.env
sudo grep -c '^CMMS_SYSTEM_USER_ID=[1-9]' /opt/odyssey-staging/.env     # expected 1
```

## 9. Host preparation (as root)

The deploy user cannot create the storage directory; the deploy script fails
the deploy unless it exists and is `odyssey:odyssey 750`.

```bash
sudo install -d -m 0750 -o odyssey -g odyssey /var/lib/odyssey-staging
sudo install -d -m 0750 -o odyssey -g odyssey /var/lib/odyssey-staging/storage
stat -c '%U:%G %a' /var/lib/odyssey-staging/storage
# expected: odyssey:odyssey 750
```

Both units must carry `StateDirectory=odyssey-staging` and
`StateDirectoryMode=0750` so systemd keeps the ownership on later starts (the
unit texts are in [STAGING_DEPLOYMENT.md](../STAGING_DEPLOYMENT.md#systemd-services)):

```bash
sudo grep -H -E '^StateDirectory(Mode)?=' \
  /etc/systemd/system/odyssey-staging.service \
  /etc/systemd/system/odyssey-staging-worker.service
# expected, four lines:
# ...odyssey-staging.service:StateDirectory=odyssey-staging
# ...odyssey-staging.service:StateDirectoryMode=0750
# ...odyssey-staging-worker.service:StateDirectory=odyssey-staging
# ...odyssey-staging-worker.service:StateDirectoryMode=0750
```

If either unit lacks them, add them under `[Service]`, then `sudo systemctl
daemon-reload` (do not start the units).

Set the environment keys in `/opt/odyssey-staging/.env` (mode `0640`, owner
`odyssey:odyssey`; edit with `sudoedit`, do not print the file):

```text
DOCUMENT_STORAGE_DRIVER=local
DOCUMENT_STORAGE_DIR=/var/lib/odyssey-staging/storage
RBAC_GLOBAL_ROLES=
```

`RBAC_GLOBAL_ROLES` is deliberately **empty** on staging (user decision): no
role is cross-company, which the isolation assertion `ISO-002` depends on.

```bash
sudo grep -E '^(DOCUMENT_STORAGE_DRIVER|DOCUMENT_STORAGE_DIR|RBAC_GLOBAL_ROLES|CMMS_SYSTEM_USER_ID)=' /opt/odyssey-staging/.env
# expected: four lines; RBAC_GLOBAL_ROLES= with nothing after the equals sign
sudo stat -c '%U:%G %a' /opt/odyssey-staging/.env      # expected: odyssey:odyssey 640
```

Also confirm `PG_DSN` in `.env` still points at the recreated database and the
owner role (the name is unchanged); `REDIS_ADDR` is the Redis you flushed.

## 12. Before every certification dispatch

The workflow invoices the certification GRN (`ErrAlreadyInvoiced` on the next
use), so **each dispatch needs a fresh un-invoiced GRN**:

```bash
# session secrets loaded as in "Session secrets" (PGPASSFILE, OWNER_DSN)
export APP_ENV=staging PG_DSN="$OWNER_DSN"
export STAGING_CERT_ADMIN_EMAIL='<admin-email>' STAGING_CERT_BRANCH_EMAIL='<branch-email>' STAGING_CERT_NO_ACCESS_EMAIL='<no-access-email>'
read -rs -p 'current admin password: '     STAGING_CERT_ADMIN_PASSWORD     && echo && export STAGING_CERT_ADMIN_PASSWORD
read -rs -p 'current branch password: '    STAGING_CERT_BRANCH_PASSWORD    && echo && export STAGING_CERT_BRANCH_PASSWORD
read -rs -p 'current no-access password: ' STAGING_CERT_NO_ACCESS_PASSWORD && echo && export STAGING_CERT_NO_ACCESS_PASSWORD

go run ./scripts/seed/staging --confirm-staging <db>@<db-host> --json > grn.json 2> grn-seed-report.txt
tail -n 2 grn-seed-report.txt
# expected: "Certification GRN: fresh grn id=<n> (po id=<n>); update STAGING_CERT_GRN_ID=<n> ..."
#   (or "reused un-invoiced grn" when the previous GRN was never used)
gh variable set STAGING_CERT_GRN_ID --env staging --body "$(jq -r .STAGING_CERT_GRN_ID grn.json)"
```

The passwords must be the current rotated values: the seeder refuses existing
users whose password differs. Do not run this on the **last day of the month**
(`FIND-031`): the period guard compares a timestamp with the period end date,
so a posting on the last day of a month can fail with `ErrInvalidPeriod` even
though the seeder reports the period present. The fix is deferred; the
mitigation is not dispatching that day.

The same item sits in section B of the
[preflight checklist](v0.10-staging-preflight-checklist.md).

- [ ] schema checksum `result=MATCH` against the fresh PG17 reference (section 6) and again after the deploy (section 11)
- [ ] every `STAGING_CERT_*` id resolves to a seeded row owned by the recorded company (section 8)
- [ ] certification role: `SELECT` works, `INSERT` refused

- [ ] the forensic dump key and SHA-256 are in `FIND-010` and appear in **no** rc.11 evidence index (`grep -r forensics <evidence index>` prints nothing)
- [ ] approval URL and date are in `FIND-020`; `FIND-020` and the `FIND-010` rebuild text are updated to `RESOLVED` only after the first clean rc.11 staging certification run (`FIND-009`)

## Rollback and roll-forward

This procedure is **roll forward only**.

- The superseded rc.10 cannot be redeployed to the rebuilt database: the host refuses a
  differing digest and the superseded rc.10 has no storage configuration. Do not try.
- The forensic dump is evidence, not a restore point. Never `pg_restore` it
  over the rebuilt database.
- If a restore is ever required, it is a **separate approved procedure**:
  `pg_restore` of the forensic dump into a **new** database name, never over
  `<db>`, and is outside this runbook.
- A failure before section 3 leaves the old database intact: restart the units
  (`systemctl start ...`) only if the user decides to abandon the rebuild.
  From section 3 on, fix forward: re-run from the failing step (a failed
  `migrate up` or checksum is fixed by dropping and recreating the empty
  database again, at most once, before escalating).
- A failed seeder run is transactional per run; rerun it after fixing the
  cause. Do not hand-edit seeded rows. Seed changes are rolled back, if needed,
  by a reviewed `DELETE` of the rows the report lists as `created`, never of
  `reused` rows.
